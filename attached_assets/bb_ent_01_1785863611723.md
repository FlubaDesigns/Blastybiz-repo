# BlastyBiz — Enterprise Readiness Handoff (Pass 01)

**Scope:** full source review — 129 files, ~39,000 lines.
`functions/index.js` (4,805 lines / 62 endpoints), `public/` (100+ pages), `firestore.rules`, `storage.rules`, `firebase.json`, `scripts/`.

**Question answered:** what stands between this codebase and enterprise-grade work?

**Summary judgment:** the security hygiene here is above average for a solo build. Magic-byte validation on uploads, HMAC-signed unsubscribe links, OAuth nonce verification, transactional AI usage gating, and a maintained field denylist in the rules are all things most codebases at this stage do not have. The gap to enterprise is **structural, not hygienic**. Fixing every bug below still leaves three blockers that require new architecture: no multi-user/RBAC model, no environment separation, and no CI.

Findings are graded:

- **P0** — blocks an enterprise deal or creates legal exposure. 9 items.
- **P1** — an enterprise security questionnaire or pen test will find it. 14 items.
- **P2** — scale, cost, and operability. 13 items.
- **P3** — maintainability and correctness. 11 items.

---

## Section 1 — Structural blockers (P0)

These are not bugs. They are missing systems. No amount of patching removes them.

### 1.1 There is no multi-user, role, or seat model

`grep` for seats, invites, team members, or roles returns nothing across the entire codebase. The data model is `users/{uid}/businesses/{bizId}` — one Firebase Auth user owns everything beneath them, permanently and exclusively.

The "Agency" plan (`index.js:2808`, `BIZ_LIMITS = { starter: 1, pro: 3, agency: 10 }`) is therefore ten businesses behind **one login and one shared password**. There is no way for an agency to give a junior staffer access to two client accounts and not the other eight. There is no way to revoke one employee without rotating the credential for everybody.

Every enterprise procurement process asks four questions this model cannot answer:

- Can we provision and deprovision individual users? — No.
- Can we scope permissions per user? — No.
- Can we see who did what? — No. `activityLogs` records `uid`, and there is only ever one uid per tenant.
- Can we connect our identity provider (SAML/OIDC/SCIM)? — No.

**What this requires:** an `organizations/{orgId}` collection above the user, a `memberships/{orgId}/{uid}` join with a role field, rules rewritten to check membership rather than path equality, and every `request.auth.uid == userId` comparison in `firestore.rules` replaced. This is the single largest piece of work in this document and it touches the entire data model. It cannot be retrofitted cheaply later — the longer real customer data accumulates under the current shape, the more expensive the migration gets.

### 1.2 There is no environment separation

`blastybiz-9523e` appears **173 times** across `public/`, `functions/`, `firestore.rules`, and `scripts/`. Cloud Function base URLs are hardcoded in 18 frontend files. OAuth redirect URIs are hardcoded in the function bodies (`index.js:1605`, `1690`). The Square webhook signature is computed against a hardcoded notification URL (`index.js:1234`).

There is one project. It is production. Every change is tested by deploying to the environment paying customers are using — `replit.md` states this explicitly: *"There is no dev server. Firebase IS the server. Deploy every time."*

An enterprise customer will ask for your change-management process. "We edit production and check whether it broke" is not an answer that passes.

**What this requires:** a second Firebase project (`blastybiz-staging`), all project-scoped strings moved to a single `config.js` on the frontend and env vars on the backend, and `.firebaserc` aliases for `staging` and `prod`.

### 1.3 There is no CI and the one release check is dead

- No `.github/` directory. No pipeline of any kind.
- One test file: `functions/test/deleteAccount.test.js` (214 lines) covering 1 of 62 endpoints.
- `scripts/check-release.cjs` resolves `PUBLIC` to `../artifacts/api-server/public` — **a path that does not exist in this repository.** The script cannot have passed in its current form. Whatever it was written to catch, it is not catching.

**What this requires:** a GitHub Actions workflow running the Firebase emulator suite, a rules test file (`@firebase/rules-unit-testing`) asserting the tenancy boundaries, and `check-release.cjs` repointed at `public/` and wired into the pipeline as a blocking step.

### 1.4 Deleting an account leaves every customer photo behind

**This is a legal exposure item, not a cleanliness item.**

The client uploads photos to `photos/{uid}/global/` and `photos/{uid}/campaigns/{cid}/` — `BlastyBiz.html:5530-5531`, and `storage.rules:5` confirms this is the active path.

`deleteAccount` (`index.js:2392-2396`) deletes:

```
users/{uid}/images/        ← legacy path
businesses/{bizId}/        ← not a path anything writes to
```

It never touches `photos/{uid}/`. **Every image a customer ever uploaded survives account deletion indefinitely.**

Under GDPR Art. 17 and CCPA this is a failure to honor erasure. It is also the kind of thing that surfaces in a security questionnaire as a direct yes/no question.

**Fix:** add `storageBucket.deleteFiles({ prefix: \`photos/${uid}/\` })` to the `storageDeletes` array. Then run a one-time reconciliation job for accounts already deleted — those files are still in the bucket right now.

### 1.5 OAuth access and refresh tokens are readable by the browser

`firestore.rules:158-160`:

```
match /platformConnections/{connId} {
  allow read: if request.auth != null && (request.auth.uid == userId || isAdmin());
```

The document stored at that path contains `accessToken` and `refreshToken` in plaintext (`index.js:1673-1679`). Firestore has **no field-level read control** — if a client can read the document, it reads every field.

The rules comment at line 157 says *"Sensitive OAuth fields ... are admin-only."* That is true for **writes** (line 167 blocks them in the diff). It is not true for reads, and the comment reads as though it is.

Consequence: any XSS on any authenticated page, any malicious browser extension, or anyone who opens the console on an unattended logged-in device can exfiltrate a long-lived Google Business Profile refresh token and a Facebook Page token. Those tokens grant posting rights to the customer's live business listings, independent of your app.

**Fix:** move secrets to `platformConnections/{connId}/private/tokens`, denied to all clients (`allow read, write: if false`). Leave `status`, `enabled`, `platformName`, `connectedAt` on the parent document for UI. Then rotate every stored token, because they have been browser-readable for the life of the deployment.

### 1.6 A browser endpoint writes to Google Secret Manager

`setOperatorSecret` (`index.js:2415`) lets an admin POST a name/value pair from `Admin-Operate.html` and writes it as a new Secret Manager version — `SQUARE_ACCESS_TOKEN`, `GOOGLE_CLIENT_SECRET`, `FACEBOOK_APP_SECRET`, `ANTHROPIC_API_KEY`, and eight more.

The allowlist on line 2424 is good. The metadata-server token fetch is correct. The problem is the existence of the path: **the highest-privilege credential store in the system is reachable from a browser**, and its only gate is the admin check described in 1.7 below. It also uses `cors: true` (wide open) rather than the `setCors` allowlist every other endpoint uses.

An enterprise reviewer will treat "secrets are writable over HTTP from a web page" as a finding regardless of how well-guarded the page is. Secret rotation belongs in `firebase functions:secrets:set` from an authenticated CLI session, with an audit trail.

**Fix:** delete the endpoint. If browser-based rotation is genuinely needed for mobile-only operation, it needs at minimum a second factor and a written record of every rotation.

### 1.7 Admin identity is an email string with no verification check

`requireAdmin` (`index.js:317`):

```js
const decoded = await verifyBearer(req);
const adminEmails = await getAdminEmails();
if (!adminEmails.includes(decoded.email)) { ... }
```

Three problems:

1. **No `email_verified` check.** The token's `email` claim is trusted regardless of whether the address was ever confirmed. For any admin address added to `config/admins` that does not yet have a registered Firebase account, an attacker who knows the address can register it via email/password and receive a token bearing that email. `auth-guard.js` enforces `emailVerified` on the frontend; `requireAdmin` on the backend does not. **The backend is the one that matters.**
2. **Admin status is not a custom claim**, so `firestore.rules` cannot use it directly and instead re-implements the check with a `get()` on `config/admins` on every evaluation (`firestore.rules:8-14`) — a billed read per rule check, and a second implementation that can drift from the first.
3. **The two implementations have already drifted.** `index.js:304` has `BOOTSTRAP_ADMIN_EMAILS = ['info@blastybiz.com', 'perceys@gmail.com']`. `firestore.rules:10` hardcodes only `info@blastybiz.com`. The second bootstrap admin has function access but not rules access.

**Fix:** set a custom claim (`admin: true`) via a CLI-run script, check `request.auth.token.admin == true` in both rules and functions, and add `if (!decoded.email_verified) throw` to `requireAdmin` today as an interim measure.

### 1.8 No CSP, no HSTS, no Permissions-Policy

`firebase.json` sets `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy`. Missing:

- **Content-Security-Policy** — the highest-value header for this codebase specifically, because of the 223 `innerHTML` assignments catalogued in Section 3.
- **Strict-Transport-Security** — Firebase Hosting serves HTTPS, but without HSTS there is no downgrade protection.
- **Permissions-Policy** — denies geolocation/camera/microphone by default.
- **Cross-Origin-Opener-Policy** / **Cross-Origin-Embedder-Policy**.

A CSP here needs care: pages load Firebase modules from `gstatic.com` and there is heavy inline scripting. Start in `Content-Security-Policy-Report-Only` mode, collect violations, then enforce.

### 1.9 The Anthropic key is a shared-environment variable

`replit.md`: *"`ANTHROPIC_API_KEY` is set as a Replit env var (shared environment)."*

A production AI credential living in a shared development environment is a finding on its own. It should exist only in Secret Manager, and the Replit copy should be revoked and rotated.

## Section 2 — Authentication and authorization (P1)

### 2.1 `suggestCategory` is a fully unauthenticated AI endpoint

`index.js:554`. No `verifyBearer`. No `reserveAiAction`. No rate limit. It accepts `{ bizName }` and makes a billed model call.

Anyone who reads your JavaScript — it is called from the client, so the URL is public — can loop this endpoint and bill your Gemini or Anthropic account until the card declines. This is the single cheapest attack against this system and it requires no account.

**Fix:** add `verifyBearer` plus `checkUidRateLimit`. Every other AI endpoint has at least a bearer check; this one was missed.

### 2.2 Six distinct authentication patterns across 62 endpoints

| Pattern | Endpoints | Example |
|---|---|---|
| `verifyBearer(req)` from header | 15 | `adaptListing:570` |
| `requireAdmin(req)` | 24 | `adminListPublishJobs:2475` |
| `idToken` in the POST **body** | 2 | `deleteAccount:2308`, `sendVerificationEmail:4568` |
| Inline hand-rolled header parse | 1 | `scoreFact:4613` |
| HMAC signature | 2 | `squareWebhook:1233`, `unsubscribeEmail:4110` |
| None | 1 | `suggestCategory:554` |

Six patterns means six places a mistake can hide, and it means no reviewer can answer "is every endpoint authenticated?" without reading all 4,805 lines — which is exactly what happened with 2.1.

**Fix:** one `withAuth(handler, { admin: false })` wrapper applied to every export. Uniformity is the control here, not any individual check.

### 2.3 `scoreFact` sets `Access-Control-Allow-Origin: *`

`index.js:4609`. Every other endpoint uses `setCors`, which validates against a four-entry allowlist (`index.js:253`). This one is open to every origin on the internet. It does verify the bearer token, so it is not a data leak, but it is an inconsistency a scanner will flag immediately.

### 2.4 The unsubscribe HMAC is keyed on the Resend API key

`makeUnsubSig` (`index.js:327`) uses `RESEND_API_KEY` as the HMAC secret. Two consequences:

- The signing key and the email-sending key are the same secret — compromise of one is compromise of both, and they have different rotation pressures.
- **Rotating the Resend key silently invalidates every unsubscribe link already sitting in customers' inboxes.** Under CAN-SPAM those links must work for 30 days after send.

**Fix:** a dedicated `UNSUB_SIGNING_KEY` secret.

### 2.5 Square webhook signature uses non-constant-time comparison

`index.js:1239`: `if (expected !== req.headers['x-square-hmacsha256-signature'])`.

`unsubscribeEmail` gets this right with `crypto.timingSafeEqual` (line 4113). The webhook — the endpoint that grants paid plan entitlements — does not. Practical exploitability over a network is low; it is a standard pen-test finding and the fix is two lines.

### 2.6 The Square webhook has no replay or idempotency guard

`index.js:1232`. Signature verification is the only gate. There is no check of `event_id` against a processed-events collection.

The plan-granting path is partially self-protecting — it deletes the `pendingCheckouts` document (line 1259) before writing, so a replay finds nothing. But the **welcome email** is sent after that point, and other branches in this 351-line handler were not audited line-by-line for the same property.

**Fix:** first action in the handler — `create()` a document at `webhookEvents/{event.event_id}`; on `ALREADY_EXISTS`, return 200 immediately.

### 2.7 `dispatchPublishJob`'s idempotency guard is not atomic

`index.js:1911-1914`, comment says *"Idempotency guard: claim the job by moving to 'processing'"*:

```js
if (job.status !== 'pending') return;
await jobRef.update({ status: 'processing', ... });
```

That is a read from the event payload followed by an unconditional write. Firestore triggers are **at-least-once** — duplicate delivery is expected behavior, not a fault. Two concurrent invocations both see `pending` in their event data and both proceed to publish.

**Consequence: duplicate posts to a customer's live Google Business Profile and Facebook Page.** For a marketing product, double-posting to a customer's public listing is a visible, embarrassing failure.

**Fix:** wrap in `db.runTransaction`, re-read the document inside the transaction, and abort if status is not still `pending`.

### 2.8 The publish trigger trusts a document field over the path

`index.js:1918`: `userBizConnsRef(job.uid, job.businessId)`.

The job document lives at `users/{userId}/businesses/{bizId}/publishJobs/{jobId}`, so `event.params.userId` and `event.params.bizId` are authoritative. `job.uid` and `job.businessId` are data. They currently agree, and `firestore.rules:151` restricts job writes to admins, so this is not presently exploitable — but it is a confused-deputy pattern one rules change away from becoming a cross-tenant write.

**Fix:** use `event.params` throughout. Same applies to `jobFailedTrigger:1984` and `jobCompletedTrigger:2065`.

### 2.9 `admin-guard.js` probes an admin endpoint to decide visibility

`admin-guard.js:29` calls `adminGetAdminEmails` and shows the page if it returns 200. This is defensible — the real enforcement is server-side. Two notes: it does not check `emailVerified` the way `auth-guard.js` does, and it means every admin page load costs a function invocation plus a Firestore read before rendering.

### 2.10 The `users` and `businesses` rules are maintained denylists

`firestore.rules:28-36` and `40-56`. The comments are admirable — they explicitly warn future maintainers to add new billing fields to the list.

The problem is the shape. **A denylist is open by default.** Any field added to a user document in the future is client-writable until someone remembers this file. The comment exists because the author already knows this is fragile.

This matters more than usual given your stated goal of handing operations to AI agents. An agent adding `trialEndsAt` to a user document has no mechanical signal that it must also edit `firestore.rules`. The convention is implicit, and an agent has to guess at it.

**Fix:** invert to an allowlist — `request.resource.data.diff(resource.data).affectedKeys().hasOnly(['displayName', 'email', 'phone', ...])`. New fields then fail closed and loudly.

## Section 3 — Client-side security (P1)

### 3.1 223 `innerHTML` assignments; at least nine interpolate unescaped

`escape-utils.js` is a genuinely good piece of work — a single canonical `escHtml` covering all five entities, with a comment explaining that scattered copies previously missed the apostrophe. Most call sites use it.

Nine do not:

| File:line | Interpolated value | Source |
|---|---|---|
| `BlastyBiz-Onboarding.html:1355` | `${bizName}` | **user input** |
| `BlastyBiz.html:4818` | `${activeName}` | **user input** |
| `BlastyBiz-Onboarding.html:830` | `${p.icon}`, `${p.name}` | config |
| `BlastyBiz-Admin-Operate.html:997` | `${stepLabel}` | Firestore config |
| `BlastyBiz-Admin-Operate.html:1053` | `${e.message}` | error |
| `BlastyBiz-Admin-Platform-Health.html:292` | `${e.message}` | error |
| `BlastyBiz-Admin-Subscriptions.html:232` | Square plan IDs | API |
| `BlastyBiz-Admin.html:260` | `${m.id}`, `${m.label}` | config |
| `BlastyBiz-TestBlasty.html:445` | `${e.message}` | error |

The first two are stored XSS on business name. Today that is self-XSS — but combine it with 1.5 (OAuth tokens readable by the same session) and self-XSS becomes token exfiltration. And the moment 1.1 lands and a business is visible to more than one user, it stops being self-XSS entirely.

**Fix:** wrap all nine in `escHtml`. Then add a `check-release.cjs` rule that fails the build on `innerHTML` + `${` without `escHtml` on the same line. That is the mechanical enforcement an AI maintainer needs.

### 3.2 Sign-out is copy-pasted across 12 pages and leaks PII on shared devices

Eleven pages carry this identical line:

```js
window.doSignOut = () => { localStorage.setItem('bb_auth','0'); signOut(auth).finally(...) };
```

Two pages (`BlastyBiz-Home.html:340`, `BlastyBiz.html:4937`) additionally clear `bb_profile` and `bb_platforms_enabled`. **The other ten do not.**

Persistent keys surviving sign-out from those ten pages:

| Key | Storage | Contents |
|---|---|---|
| `bb_profile` | localStorage | owner name, business name, phone, address |
| `bb_trial_email` | localStorage | email address |
| `bb_trial_name` | localStorage | name |
| `bb_platforms_enabled` | localStorage | platform selections |

Sign out from Dashboard, Plan-Pro, About, Contact, Privacy, AI, or Plan-Agency on a shared or library machine and the next user reads the previous user's name, business, phone, and address out of `localStorage`.

Cleanup calls are scattered across 16 sites in 8 files with no owner.

**Fix:** one `session.js` exporting `signOutAndClear()` with a single `BB_KEYS` array. Import everywhere. Delete the eleven copies.

### 3.3 Magic-link trial sign-in cannot write its user document

`BlastyBiz.html:4951`:

```js
await setDoc(doc(db, 'users', result.user.uid), {
  plan: 'trial', displayName: _mlName, email: _mlEmail, createdAt: ...
}, { merge: true });
```

`firestore.rules:23` requires `request.resource.data.plan == 'starter'` on create. Line 32 blocks `plan` in the diff on update. **Both branches deny this write.** The failure lands in `.catch(e => console.error(...))` on line 4963 and is invisible to the user.

Every magic-link trial signup produces an authenticated user with no user document — no plan, no email, no display name.

### 3.4 `_mlName` is always empty

`BlastyBiz.html:4950`:

```js
const _mlName = window.localStorage.removeItem('bb_trial_name') || '';
```

`removeItem()` returns `undefined`. `_mlName` is unconditionally `''`. It needs a `getItem` before the `removeItem`. (Line 4949 immediately above does it correctly for the email.)

### 3.5 Client uploads bypass the hardened server upload path

`uploadImage` (`index.js:1004`) is thorough: MIME allowlist, base64 validation, 5 MB cap, magic-byte signature checks for JPEG/PNG/WebP/GIF, filename sanitization. Good code.

The client does not use it. `BlastyBiz.html:5558` calls `uploadBytesResumable` directly to `photos/{uid}/...`, governed only by `storage.rules:8`, which checks `request.resource.contentType.matches('image/.*')` — **a client-supplied header.** A polyglot or a renamed file passes.

Either route uploads through the function, or port the magic-byte check client-side and accept that it is advisory.

### 3.6 Ten-year signed URLs

`index.js:1041`: `expires: new Date(Date.now() + 10 * 365 * 24 * 3600 * 1000)`.

An effectively permanent, unauthenticated, unrevocable public URL per image. These get handed to Google and Facebook APIs, so they cannot be short-lived without a re-signing step — but ten years is a data-governance answer you do not want to give in a questionnaire. Consider a signing proxy endpoint, or at minimum document the tradeoff.

## Section 4 — Scale and cost (P2)

### 4.1 No instance, concurrency, or memory limits anywhere

Zero occurrences of `maxInstances`, `concurrency`, `memory`, or `cpu` across all 62 functions. No `setGlobalOptions` call.

Firebase Functions v2 will scale to 1,000 instances by default. Combined with 2.1 (unauthenticated AI endpoint), a single afternoon of abuse produces an unbounded bill against your Anthropic/Gemini keys and your Blaze account, with nothing in the code to stop it.

**Fix today, before anything else in this document:** `setGlobalOptions({ maxInstances: 10 })` at the top of `index.js`, then raise selectively. Also set a GCP budget alert — that is a console action, not a code one.

### 4.2 Five unbounded collection scans

| Location | Query |
|---|---|
| `index.js:3081` | `db.collection('users').get()` — **entire user table** |
| `index.js:2969` | `users where onboarded == false` — no limit |
| `index.js:2484` | `collectionGroup('publishJobs').get()` — **every job ever** |
| `index.js:2621` | `collectionGroup('platformConnections').get()` |
| `index.js:2633` | `collectionGroup('platformConnections').get()` |

Each loads every matching document into function memory. At a few hundred users these are fine. At ten thousand they exceed memory, time out, and bill for a full read of the collection on every admin page load. `adminListBusinesses:2613` gets this right with `.limit(200)` — that pattern needs to reach the other five.

### 4.3 N+1 reads in the scheduled jobs

`scheduledUpgradeNudge`, `scheduledWeeklyDigest`, `scheduledSetupNudge`, and `checkPlatformTokenExpiry` all loop a collection and issue `db.collection('users').doc(uid).get()` per iteration (lines 2754, 2819, 3614 and others). Use `getAll()` batched at 500, or denormalize the two or three fields needed onto the document being iterated.

### 4.4 Entitlements are defined in three places, none authoritative

| Thing | Where | Overridable? |
|---|---|---|
| AI action caps | `index.js:332` hardcoded | No |
| Business count caps | `index.js:2808` hardcoded | Partially — `agencyMax` from Firestore |
| Prices | `index.js:1142` hardcoded | Partially — from Firestore |

Changing a plan limit means a code change and a functions redeploy. For an AI-operated system this is exactly backwards: entitlements should be data an agent can read and validate, not constants buried at three different line numbers.

**Fix:** one `config/plans` document, one `getPlanConfig()` accessor with the hardcoded values as fallback defaults.

### 4.5 The `trial` plan does not exist on the backend

Ten frontend comparisons against `'trial'`. **Zero backend references.** `AI_LIMITS` (`index.js:332`) has `starter`, `pro`, `agency` only — a trial user falls through `AI_LIMITS[plan] || AI_LIMITS.starter` to the 10-action starter cap. `BIZ_LIMITS` (2808) has the same gap.

So the frontend shows trial users trial affordances and the backend silently meters them as starter. Combined with 3.3 (trial user documents never write at all), the entire trial tier is in an undefined state.

### 4.6 `checkUidRateLimit` has a read-then-write race

`index.js:262-280` reads the counter, then updates it. Concurrent requests all read the same value and all pass. The limits are generous (20/hour on OAuth init, 5/hour on verification emails) so the practical impact is small, but it should be a transaction.

Also worth noting: the `catch` returns `false`, so a Firestore outage denies all rate-limited actions. The comment says this is deliberate ("fails closed"), which is the right call — flagging it only so nobody "fixes" it later.

### 4.7 No dead-letter queue or retry policy on publish jobs

`dispatchPublishJob` catches, writes `status: 'failed'`, and stops. No retry, no backoff, no `retry: true` in the trigger config. A transient Google API 503 permanently fails a customer's post, and recovery depends on an admin noticing it in `Admin-Failed-Jobs.html` and clicking retry.

`adminRetryJob` (`index.js:2502`) exists, which is good — but manual retry is not an availability story for enterprise.

### 4.8 No observability

111 `console.*` calls into Cloud Logging. No error tracker, no alerting, no uptime monitoring, no structured log schema, no trace IDs. When a customer reports "my post didn't go out," the only tool is grep across Cloud Logging by timestamp.

Enterprise contracts carry SLAs. You cannot report against an SLA you do not measure. Minimum viable: Sentry or Error Reporting on the functions, a structured logger emitting `{ severity, uid, bizId, jobId, fn }`, and an alert on failed-job rate.

### 4.9 No documented backup or recovery posture

No mention of Firestore PITR, no scheduled export, no tested restore. "What is your RPO/RTO?" is a standard questionnaire question. Enable PITR (7-day window, console setting), add a scheduled export to GCS, and — the part everyone skips — actually perform a restore into staging once and write down how long it took.

## Section 5 — Architecture and maintainability (P2/P3)

### 5.1 `functions/index.js` is 4,805 lines and 62 endpoints in one file

Payments, OAuth, AI, publishing, email, admin, and eight scheduled jobs share one module. Consequences that matter operationally:

- Every deploy redeploys all 62 functions. A copy tweak in an email template redeploys the payment webhook.
- Every function loads every dependency at cold start — Anthropic SDK, axios, Square, firebase-admin.
- The secrets array is per-function, but the blast radius of an edit is the whole file.
- No module boundary means no unit test boundary, which is part of why there is one test.

Split into `payments/`, `oauth/`, `ai/`, `publishing/`, `admin/`, `scheduled/`, `lib/`, with `index.js` as a re-export barrel. This is mechanical and low-risk, and it makes everything else in this document easier to work on.

### 5.2 `BlastyBiz.html` is 6,653 lines

The main application is a single HTML file with inline modules. It exceeds what can be reasoned about in one sitting, and it is where both bugs in 3.3 and 3.4 are hiding. At minimum, extract the module scripts into separate `.js` files under `public/js/` so they can be linted and diffed independently. This does not require a build step.

### 5.3 Dependencies are pinned but unmanaged

`functions/package.json` pins exact versions (good — reproducible builds). But there is no Dependabot, no `npm audit` in any pipeline, and no stated upgrade cadence. `firebase-admin@12.7.0` and `@anthropic-ai/sdk@0.36.3` are both several releases behind. Enterprise reviewers ask how you learn about a CVE in a dependency; right now the answer is that you do not.

### 5.4 The frontend loads Firebase from a CDN with no SRI

`https://www.gstatic.com/firebasejs/10.12.0/...` appears in every page with no `integrity` attribute. Google's CDN is a reasonable trust anchor, but SRI is free and questionnaires ask about it. The version string is also duplicated across ~40 files — a single upgrade is a 40-file edit.

### 5.5 `check-release.cjs` is broken and under-scoped

Beyond the dead path (1.3), the three checks it implements — orphan pages, duplicate escape functions, asset version drift — are useful but do not cover the failure modes that actually bit this codebase: unescaped `innerHTML`, missing auth wrappers, storage-path drift between writer and deleter, plan-string vocabulary drift. Those are all mechanically detectable and all appear in this document.

This is the highest-leverage item for your AI-operations goal. An agent will not reliably remember conventions; it will reliably obey a failing build.

### 5.6 `replit.md` documents a workflow that cannot be verified

Steps 6 and 7 of the mandatory fix workflow reference `download/BlastyBiz_Audit.md` and `download/BlastyBiz_Site.zip`. Neither path exists in this archive. Either the workflow is not being followed or the artifacts are outside the repo — either way, an onboarding engineer reading `replit.md` will follow instructions that fail.

## Closing note

The distance from here to "solid production SaaS" is roughly items 1–23: a few weeks of focused work, all of it well-defined, none of it requiring new architecture.

The distance from there to "enterprise" is item 24, and it is a different kind of distance. Six of the eleven procurement requirements in Section 6 cannot be started until the organization model exists. That work gets more expensive every month real customer data accumulates under the current single-tenant shape.

If enterprise is the destination, item 24 should be scheduled deliberately rather than deferred — not because it is urgent this week, but because it is the only item on this list whose cost is actively increasing.
