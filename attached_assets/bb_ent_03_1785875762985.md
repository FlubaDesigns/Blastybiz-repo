# BlastyBiz — Production Gate (Pass 03)

**Scope:** what must be fixed before taking paying customers. Narrower than Pass 01 and 02 on purpose.

Pass 01 and 02 answered *"what stands between this and enterprise?"* — 47 items, most of them structural. This pass answers a different and more urgent question: **what breaks if you go live tomorrow?**

The answer is four things. Everything else on the open list is enterprise-tier and does not stop you charging money.

**Method note:** this pass was produced by checking which files Node actually loads at runtime, not by reading the ones that look canonical. That distinction is the whole reason for §2 below.

## The gate — four items

| # | Item | Failure mode |

| 1 | Broken re-export barrel | Nothing deploys at all |
| 2 | 13 dead `lib/` files duplicating the live one | Silent config drift; future fixes land in files that never run |

## 1. Broken re-export barrel — deploy blocker

Carried from Pass 02 §0. Restated here because nothing else in this document matters until it is done.

`functions/index.js` lines 32–38 require directories that do not exist. Modules live at `functions/modules/*.js`; the barrel asks for `./ai`, `./payments`, `./oauth`, `./publishing`, `./admin`, `./scheduled`, `./user`.

Two faults: the missing `./modules/` path segment, and `./user`, which corresponds to no file. The user-lifecycle code lives in `modules/business.js` (`createBusiness`, `deleteBusiness`, `deleteAccount`, `sendVerificationEmail`) and `modules/misc.js` (`sendTestEmail`, `contactForm`, `unsubscribeEmail`).

Because Firebase loads `index.js` to enumerate exports at deploy time, the first failed `require` aborts the whole deploy. All 61 functions fail, not one.

**Fix — replace lines 32–38:**

```js
Object.assign(exports, require('./modules/ai'));
Object.assign(exports, require('./modules/payments'));
Object.assign(exports, require('./modules/oauth'));
Object.assign(exports, require('./modules/publishing'));
Object.assign(exports, require('./modules/admin'));
Object.assign(exports, require('./modules/scheduled'));
Object.assign(exports, require('./modules/business'));
Object.assign(exports, require('./modules/misc'));
```

Seven requires become eight. **Do not drop `misc`** — it holds `unsubscribeEmail`, the CAN-SPAM target in every email already sent.

Also correct the header comment at lines 7–15, which documents the non-existent layout and is the reason the requires read as plausible.

**Verify:**

```bash
cd functions && node -e "console.log(Object.keys(require('./index.js')).length)"
```

Expect **61**.

**Cross-module requires are fine** — `admin.js` imports the three publisher helpers from `publishing.js`, and `scheduled.js` imports `fetchAndCacheYelpCategories` from `admin.js`. Both are exported at the bottom of their modules, and there is no cycle (`publishing.js` does not import `admin.js`). Nothing to change.

`lib/shared.js` does not require any of them. It is a self-contained 574-line module holding its own copy of everything.

### First, the reassurance

I re-verified every Pass 02 "fixed" claim against `lib/shared.js` specifically — the file that actually runs. **All of them are in the live copy:**

- `_unsubSecret()` with `UNSUB_SIGNING_KEY` — `shared.js:361`
- `checkUidRateLimit` transactional — verified in `shared.js`
- `getPlanConfig` with `trial` in both `aiLimits` and `bizLimits` — `shared.js:367`
- `withAuth`, `bbLog`, `_getConnTokens` / `_setConnTokens` — all exported from `shared.js:557+`

Nothing reported as fixed is fixed only in a dead file. The Pass 02 status table stands.

### Now the problem

You have two copies of every helper, and the one that *looks* canonical is not the one that runs.

The failure this produces is specific and quiet. Someone — human or agent — opens `lib/plans.js` to change the Pro plan's AI cap from 100 to 200, because that is obviously where plan config lives. They save, deploy, and the cap stays at 100. There is no error. There is no warning. The file they edited is never loaded.

The same applies to every security helper. A future hardening of `requireAdmin` in `lib/auth.js` would leave the live `requireAdmin` in `shared.js` untouched, and the deploy would look clean.

This is the highest-risk item in this document for your stated goal of agent-operated maintenance. An agent asked to "update the rate limit" will find `lib/rateLimit.js`, edit it correctly, and report success. It will be wrong, and nothing in the toolchain will say so.

### Fix — pick one, do not leave both

**Option A — delete (fastest).** Remove the 13 unimported files. `shared.js` is complete and correct. This is a one-command change and loses nothing, but leaves a 574-line monolith and gives up the modularity the refactor was for.

**Option B — finish the refactor (correct).** Convert `shared.js` into a pure re-export barrel over the 13 split files, delete its duplicate implementations, and keep the module import lines exactly as they are:

```js
// lib/shared.js — re-export barrel. No implementations live here.
module.exports = {
  ...require('./db'),
  ...require('./auth'),
  ...require('./ai'),
  ...require('./plans'),
  ...require('./rateLimit'),
  ...require('./unsub'),
  ...require('./email'),
  ...require('./logging'),
  ...require('./platforms'),
  ...require('./publishers'),
  ...require('./square'),
  ...require('./yelp'),
  ...require('./config'),
};
```

Before doing this, diff each pair — the copies have already diverged in at least one place (`lib/unsub.js` carries the `_unsubSecret` fallback comment that `shared.js` implements slightly differently), so the split files are not guaranteed to be byte-equivalent to the live behaviour. **Take `shared.js` as the source of truth for any difference**, since it is what has been running.

Option B is a few hours and gets you the modularity. Option A is ten minutes and gets you correctness. Either beats the current state; both is not an option.

### Minor, same cause

`setGlobalOptions({ maxInstances: 10 })` is called twice — `index.js:29` and `shared.js:15`. Harmless (the second is a no-op overwrite with identical values), but it is the same duplication showing up in config. Keep the one in `index.js`; drop it from `shared.js`.

## 3. `reserveAiAction` throws on users with no document

**`lib/shared.js:191–213`.**

```js
async function reserveAiAction(uid) {
  return db.runTransaction(async (tx) => {
    const userRef = db.collection('users').doc(uid);
    const snap    = await tx.get(userRef);
    const data    = snap.exists ? snap.data() : {};   // ← handles missing doc
    ...
    if (needsReset) {
      tx.update(userRef, { ... });                    // ← 209: throws if missing
    } else {
      tx.update(userRef, { ... });                    // ← 216: throws if missing
    }
```

Line 195 correctly anticipates a missing user document and defaults to `{}`. Lines 209 and 216 then call `tx.update()`, which in Firestore **throws `NOT_FOUND` (code 5) on a document that does not exist** — it does not create one. `set()` creates; `update()` does not.

So the missing-document case is handled halfway: the read tolerates it, the write does not.

**Who has no user document?** Anyone whose `users/{uid}` create failed. Until Pass 01 §3.3, that was **every magic-link trial signup** — the client wrote `plan: 'trial'` and Firestore rules rejected it, with the error swallowed by a `.catch(console.error)`. Those accounts exist right now, authenticated, with no user document. Every one of them hits a hard 500 on their first AI action rather than being metered at the trial cap.

It also covers any future case where the create write races or fails, which is exactly the kind of thing a signup flow does under load.

**Fix — change both calls to `set` with merge:**

```js
    if (needsReset) {
      tx.set(userRef, {
        aiActionsUsed: 1,
        aiActionsResetAt: admin.firestore.Timestamp.fromDate(
          new Date(now.getTime() + 30 * 24 * 60 * 60 * 1000)
        ),
      }, { merge: true });
    } else {
      tx.set(userRef, {
        aiActionsUsed: admin.firestore.FieldValue.increment(1),
      }, { merge: true });
    }
```

`FieldValue.increment` works correctly inside `set(..., { merge: true })` on a missing document — it treats the absent field as 0. No other change needed.

**Note:** if you take Option B in §2, this fix belongs in `lib/ai.js`, which holds the other copy of `reserveAiAction`. Fix it in whichever file survives — and check the other copy has the same bug before deleting it.

**Worth doing alongside:** a one-time backfill creating `users/{uid}` documents for authenticated users who lack one. Those accounts are currently in a half-state — they can log in but have no plan, no email, and no display name on record.

## 4. `private/tokens` survives account deletion

Carried from Pass 02. Still open.

**`modules/business.js:120–128`.** The deletion routine gathers subcollections per business:

```js
const [draftsSnap, jobsSnap, connsSnap, pendingSnap, libSnap,
       bizFactsSnap, bizImagesSnap] = await Promise.all([
  userBizDraftsRef(uid, bizId).get(),
  userBizJobsRef(uid, bizId).get(),
  userBizConnsRef(uid, bizId).get(),      // ← 124: parent conn docs only
  ...
```

`connsSnap` holds the parent `platformConnections` documents. Since Pass 01 §1.5, the OAuth access and refresh tokens live in a `private` subcollection *beneath* each of those documents — and **Firestore does not cascade-delete subcollections when a parent document is deleted.**

Result: every account deletion leaves live OAuth refresh tokens in Firestore as orphaned documents, unreachable through the console's normal tree view and invisible to the deletion path.

This is the same class of failure as the photos gap in Pass 01 §1.4, created by the fix for §1.5. It is also the exact scenario the erasure fix was meant to close.

**Fix — inside the `for (const bizDoc of bizSnap.docs)` loop, after `connsSnap` is populated:**

```js
for (const connDoc of connsSnap.docs) {
  const privSnap = await connDoc.ref.collection('private').get();
  privSnap.docs.forEach(d => bizSubRefs.push(d.ref));
}
```

**Then sweep.** Every account deleted since the token move has left tokens behind. They are in Firestore now. A one-time script over `collectionGroup('private')` checking for orphaned parents will find them.

**Related, worth confirming while you are in this code:** the tokens themselves should be revoked at the provider, not just deleted locally. `disconnectPlatform` already does best-effort revocation against Google and Facebook. `deleteAccount` should do the same before deleting the documents — otherwise the tokens remain valid at Google and Facebook even after they vanish from your database.

## Strongly recommended, not strictly blocking

### Repoint `check-release.cjs` and add the barrel check

`scripts/check-release.cjs` still resolves `PUBLIC` to `../artifacts/api-server/public`, a path that does not exist in this repo. It cannot have run.

Item 1 of this document — a bug that takes down all 61 functions — would have been caught by one line:

```js
const exported = Object.keys(require('../functions/index.js')).length;
if (exported < 61) fail(`Barrel exports ${exported}, expected 61`);
```

Item 2 would have been caught by a second:

```js
// every file in lib/ must be imported by something
```

Both are trivial. Neither exists. This is the difference between a codebase that catches its own mistakes and one that relies on an auditor noticing — and you should not be paying for the second option indefinitely.

Repoint the script at `public/`, add those two checks, and run it from a GitHub Action. A few hours, and it is the item most likely to prevent the next Pass.

### Confirm two rotations happened

Neither is visible in source, so I cannot verify either:

1. **OAuth access and refresh tokens** — these were readable by the browser before Pass 01 §1.5. Moving them to a private subcollection protects them going forward but does nothing about tokens already exposed. They need to be revoked and re-consented.
2. **`ANTHROPIC_API_KEY`** — `replit.md` documents it as living in a shared Replit environment. It should exist only in Secret Manager, with the Replit copy revoked.

If either has not happened, do it before launch. Both are console work, not code.

### Four unbounded admin queries

`modules/admin.js` lines 157, 368, 371, and 489. Lines 368 and 371 sit in the same handler, so one admin page load reads the entire `users` collection **and** every publish job ever created.

Not a launch blocker at your current size — it will be a bill and a timeout at a few thousand users. Add `.limit()` before that becomes true, not after.

## Closing

Four items, and two of them are one-line-class fixes. That is a short list for a codebase this size, and it reflects that Passes 01 and 02 closed 20 of 47 items including the whole P0 security tranche.

The thread connecting items 1, 2, and the `check-release.cjs` note is worth naming: **all three are correctness problems that reading the code cannot catch.** The barrel looks right. `lib/plans.js` looks canonical. `check-release.cjs` looks like it runs. Each is wrong in a way that only execution reveals.

You have reached the size where that is the dominant failure mode. Not bad logic — logic that is fine in isolation and wrong about which file, which path, or which copy is real. Tests and a build gate stop being process hygiene at this point and become the only mechanism that can tell you whether a change did anything at all. That matters doubly given where you are taking this: an agent will confidently edit the wrong file and report success, and only a failing build will disagree with it.
