# BlastyBiz — Production Gate (Pass 04)

**Scope:** verification of the Pass 03 gate, plus a config-drift diff of all 61 functions against their pre-refactor definitions.

**Verdict: not ready.** All four Pass 03 blockers are correctly closed. This pass introduced three new problems, one of which silently disables a user-facing feature.

**Method:** every function's deploy configuration — secrets, region, schedule, invoker, trigger type — was extracted from the pre-refactor `index.js` and diffed against the current modules. That is how items 2 and 3 below surfaced. They are invisible in a normal code review because each change looks reasonable in isolation.

## Part 2 — Three new problems

### 2.1 Scheduled posting is disconnected end to end

**Severity: user-facing feature silently dead. Highest priority in this document.**

`scheduledPostingCheck` was rewritten. It now reads:

```js
// modules/scheduled.js:120
const snap = await db.collectionGroup('scheduledPosts')
  .where('status', '==', 'active')
  .where('nextRunAt', '<=', now)
  .limit(50)
  .get();
```

**Nothing writes `scheduledPosts.`** Verified across the entire repository — no frontend write, no Cloud Function write, no entry in `firestore.rules`, no entry in `firestore.indexes.json`. The only reference to the collection anywhere is the query that reads it.

Meanwhile the frontend still writes schedules the old way, onto listing drafts:

```
public/BlastyBiz.html:2866   schedule: currentSchedule,
public/BlastyBiz.html:3240   window._bbUpdateDraft(draftId, { schedule: s })
public/BlastyBiz.html:3474   window._bbUpdateDraft(did, { schedule: payload })
```

And the reader that consumed those — the `collectionGroup('listingDrafts').where('schedule.enabled', '==', true)` loop in the pre-refactor `scheduledPostingCheck` — was deleted. `grep` for `schedule.enabled` across `functions/` and `public/` returns nothing.

**Net effect:** a user opens the schedule tab, sets a cadence, saves. The write succeeds. The UI confirms it. Firestore holds the data. The backend will never look at it, and the collection the backend does look at will never have anything in it. **No error is thrown anywhere in this chain.** The failure is completely silent on both sides.

For a product whose core promise is automated posting, this is the worst possible thing to ship broken.

**Three sub-problems, in order:**

1. **No writer.** Either the frontend must be updated to write `scheduledPosts` documents, or `scheduledPostingCheck` must be pointed back at `listingDrafts`. This is a product decision, not a mechanical fix — the new shape (`{ uid, bizId, platformId, content, imageUrls, status, nextRunAt, frequency }`) is arguably cleaner than schedule-embedded-in-draft, but it needs the other half built.
2. **No rules.** `firestore.rules` has no `scheduledPosts` match block. Under the default-deny at the bottom of the rules file, any client write would be rejected — so even after the frontend is updated, this must land first.
3. **No index.** A `collectionGroup` query filtering on `status` and range-filtering on `nextRunAt` requires a composite index. Without it the query throws `FAILED_PRECONDITION` at runtime — caught by the outer `try` at scheduled.js:119 and logged, so the job appears to run cleanly while doing nothing.

**Also:** `.limit(50)` with no cursor. The pre-refactor version paginated with `startAfter` through the full result set. Above 50 due schedules, the remainder are skipped every run and never catch up, since each run re-reads the same oldest 50. Restore the pagination loop, or at minimum order by `nextRunAt` ascending so the backlog drains in a defined order.

### 2.2 Both Yelp functions lost their API key

`refreshYelpCategories` — `modules/admin.js:555`:

```js
exports.refreshYelpCategories = onRequest({ invoker: 'public' }, async (req, res) => {
```

Pre-refactor (`index.js:3511`):

```js
exports.refreshYelpCategories = onRequest(
  { invoker: 'public', region: 'us-central1', secrets: ['YELP_API_KEY'] },
```

`scheduledYelpCategoryRefresh` — `modules/scheduled.js:160`:

```js
exports.scheduledYelpCategoryRefresh = onSchedule(
  { schedule: 'every 720 hours', region: 'us-central1' },
```

Pre-refactor (`index.js:3858`):

```js
  { schedule: 'every monday 03:00', timeZone: 'America/New_York',
    region: 'us-central1', secrets: ['YELP_API_KEY'] },
```

The shared implementation still reads the key:

```js
// modules/admin.js:572, inside fetchAndCacheYelpCategories
headers: { Authorization: `Bearer ${process.env.YELP_API_KEY}` },
```

Without the secret declared, Cloud Functions v2 does not mount it. `process.env.YELP_API_KEY` is `undefined`, the header becomes `Bearer undefined`, and Yelp returns 401. Category refresh fails on both the manual admin path and the cron.

**Fix:** restore `secrets: ['YELP_API_KEY']` to both declarations. Restore `region: 'us-central1'` to `refreshYelpCategories` — v2 defaults to `us-central1` so behaviour is likely unchanged, but it should be explicit and match the rest of the file.

**This is the same class of bug as the Pass 02 barrel:** something that only exists at deploy/runtime, invisible in a code diff, and undetectable by reading. The function body is correct. The wiring is not.

### 2.3 Five cron schedules changed with no stated rationale

| Function | Before | After |
|---|---|---|
| `scheduledYelpCategoryRefresh` | `every monday 03:00`, TZ America/New_York | `every 720 hours`, **no timeZone** |
| `scheduledSetupNudge` | `every day 09:00` | `every 6 hours` |
| `scheduledUpgradeNudge` | `every day 10:00` | `every monday 09:00` |
| `scheduledWeeklyDigest` | `every monday 08:00` | `every monday 09:30` |
| `scheduledPostingCheck` | `every 1 hours` | `every 30 minutes` |

Some of these are plausibly deliberate retuning. From outside the change, there is no way to tell which — and two have direct customer impact:

- **`scheduledSetupNudge` at every 6 hours** is a nudge email job. Unless its internal guard is airtight, users who haven't finished setup now receive prompts **four times a day** instead of once. That is a deliverability and complaint risk, and it is the kind of change that surfaces through angry replies rather than logs.
- **Loss of `timeZone` on the Yelp job.** Without it, Cloud Scheduler defaults to UTC. Combined with `every 720 hours` (a 30-day interval anchored to deploy time rather than a calendar slot), the job no longer runs at a predictable local time.

**Action:** confirm each of the five was intentional. Restore any that were not, and restore `timeZone: 'America/New_York'` on the Yelp job regardless. If they were intentional, note it — an unexplained cadence change is indistinguishable from an accident on the next review.

## Part 3 — The process

The four gate items closed cleanly and correctly. Then a scheduling-subsystem rewrite rode along in the same pass and broke a working feature. That sequence is the whole story of this document, and it is worth being direct about.

### What is working

The fixes themselves have been consistently high quality across four passes. Not one has been a patch-over. Specifically:

- `getPlanConfig` fails soft to hardcoded defaults, so a config-read failure doesn't lock every user out of their plan.
- `retry: true` and the transactional job claim were landed together, because either alone would have been wrong.
- OAuth revocation happens *before* document deletion, with a comment explaining the ordering.
- The `tx.set` vs `tx.update` fix carries a comment explaining the Firestore semantics rather than restating the code.

That is someone who understood each problem rather than pattern-matching the fix. Twenty-plus items closed with essentially zero rework is a good rate.

### What is not working

**The same failure mode has now recurred in four consecutive passes, and it is always the same shape: a change that reading the code cannot catch.**

| Pass | Bug | Would execution have caught it? |
|---|---|---|
| 02 | Barrel requiring directories that don't exist | Instantly — `MODULE_NOT_FOUND` on load |
| 03 | 13 dead `lib/` files; canonical-looking file wasn't the live one | Yes — an import-graph check is one script |
| 04 | `scheduledPosts` has no writer, no rules, no index | Yes — first emulator run returns empty / throws `FAILED_PRECONDITION` |
| 04 | Yelp secret dropped from both declarations | Yes — first invocation returns 401 |

Four for four. Every one of these dies immediately on execution. Not one is visible in a diff, because in every case **the code is correct and the wiring is wrong.** That is the specific blind spot: reading verifies logic, and none of these were logic errors.

### Two causes

**1. Nothing in the loop ever runs the code.** This is not a discipline problem — there is no mechanism. No emulator, no smoke test, no CI. `check-release.cjs` still resolves `PUBLIC` to `../artifacts/api-server/public`, a path that does not exist, so it cannot have run either. `replit.md` states it plainly: *"There is no dev server. Firebase IS the server. Deploy every time."* Every validation in this project is currently a human or a model reading text.

**2. Unrelated work rode along in a remediation pass.** Pass 03 defined four bounded fixes. Those four were done correctly. A scheduling rewrite also happened, and that is where the regression came from. Remediation passes need to be boring and small, or they become their own source of bugs — which is precisely what happened here.

### The structural point

The audit loop has hit diminishing returns. This pass, I mostly found bugs that the previous fix round introduced. That is a treadmill, and I am a slow and expensive way to run it.

Worth stating plainly: **everything I have reported across four passes is static analysis. I have never seen this code execute.** I read files and reason about them. That has been useful — it found SSRF-class issues, the erasure gaps, the barrel, the dead libs — but it is structurally incapable of catching a whole category of problem, and it is far slower than the alternative.

A single `firebase emulators:start` plus a script hitting every endpoint once would have caught more of Pass 04 than I did, in seconds, and would keep doing so forever without being asked.

### Recommendation

**Do not run another audit pass next.** Fix the three items in Part 2, then spend the following block of work on execution:

1. **Firebase emulator suite** running locally — Firestore, Functions, Auth. Even without a full test suite, `emulators:start` alone would have caught the Yelp secret loss and the missing `scheduledPosts` index on the first run.
2. **A smoke script** that calls every endpoint once with a dummy auth token and asserts a non-5xx response. Roughly 60 lines. It catches the barrel class, the wiring class, and the secret class permanently.
3. **Repoint `check-release.cjs`** at `public/` and add three checks: barrel export count equals 61; every file in `lib/` and `modules/` is imported by something; every collection read by a Cloud Function has a `firestore.rules` match block. That last one catches 2.1 directly.
4. **Rules unit tests** (`@firebase/rules-unit-testing`) asserting the tenancy boundaries — the highest-value tests in the project, since the rules are the actual security boundary.
5. **A GitHub Action** running all of the above on push.

Item 3 alone would have caught two of the four problems in this document.

This matters more for BlastyBiz than for a typical codebase because of where you are taking it. An AI agent maintaining these platforms will confidently edit the wrong file, drop a secret, or point a query at a collection nothing writes — and report success every time. A failing build is the only thing that will disagree with it. Every convention currently living in a comment is a bug an agent will eventually write. Three of the four items in this document already prove that, and they were written by people.

## Closing

Four passes in, the security posture is materially better than where this started and the individual engineering has been good. What has not improved at all is the ability to tell whether a change worked — and that is now the binding constraint on everything else.

The scheduling break is the clearest illustration available. A user can save a schedule today, see it confirmed, and have it never run, with no error surfaced anywhere on either side of the system. Nobody did anything careless. The rewrite is arguably better designed than what it replaced. It just wasn't finished, and there is nothing in the project that could have said so.

Fix the three items. Then build the thing that catches the fourth one before I do.
