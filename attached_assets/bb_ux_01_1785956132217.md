# BlastyBiz — UX Spec 01: Six Friction Reducers

**Purpose:** implementable specs for six changes that reduce the effort required of a business owner to get an AI-generated ad onto a platform.

**Framing:** BlastyBiz's promise is "we write and post your ads." Today the product delivers on that, but only after the owner does a meaningful amount of typing, deciding, and navigating. Every spec below moves work from the owner to the system.

**Ordering principle:** ranked by friction removed per unit of build effort. Specs 1 and 2 are the highest-leverage and cheapest. Spec 3 is the largest change and the most transformative.

**Codebase facts these specs are built on** (verified in the V1 build):

- `aiContext` is a 5-field map on the business document — `story`, `different`, `awards`, `customer`, `other` — stored at `users/{uid}/businesses/{bizId}.aiContext` and consumed at `modules/ai.js:133–143`
- `adaptListing` (`modules/ai.js:96`) takes `{ listing, platforms, tone, platformCats }` and has request dedup via `aiRequestDedup`
- `suggestCategory` (`modules/ai.js:79`) infers a category from `bizName` alone
- Drafts live at `users/{uid}/businesses/{bizId}/listingDrafts/{id}` with `adaptations` (per-platform copy), `imageUrls`, and a `schedule` map
- Google OAuth already requests `https://www.googleapis.com/auth/business.manage` (`modules/oauth.js:35`) and resolves account + location IDs
- `makeUnsubSig` + `timingSafeEqual` (`modules/misc.js:117–122`) is a working signed-link pattern
- One-tap copy-and-open-tab for manual platforms already exists (`BlastyBiz.html:1599`)
- Storage path for photos is `photos/{uid}/global/` and `photos/{uid}/campaigns/{cid}/`

## Spec 1 — Show the ad before asking for anything

**Effort: Medium (1 new page, 1 endpoint change). Impact: Highest.**

### Problem

The current path to a first generated ad is Intro → Trial → Profile → CreateBiz → Onboard2 → Story. Five or six screens of the system asking and the owner typing, before the owner sees a single thing the product actually makes.

Every screen before the payoff is an exit. And the payoff is the entire pitch — "AI writes your ads" is abstract until you watch it happen with your own business name in it.

### Solution

A single pre-auth page. Business name, city, one button. Twenty seconds later, three real ads. Then the ask.

```
┌──────────────────────────────┐
│  What's your business called?│
│  ┌────────────────────────┐  │
│  │ Perry's Auto Repair    │  │
│  └────────────────────────┘  │
│  ┌────────────────────────┐  │
│  │ Toledo, OH             │  │
│  └────────────────────────┘  │
│                              │
│     [ Show me my ads → ]     │
└──────────────────────────────┘
```

Then, on the same page, without navigation:

```
┌──────────────────────────────┐
│ Here's what we'd post for you│
│                              │
│ ▸ Google Business Profile    │
│   "Toledo drivers have..."   │
│ ▸ Facebook                   │
│   "Winter's coming and..."   │
│ ▸ Instagram                  │
│   "Same hands on your car..."│
│                              │
│  [ Save these — free trial ] │
│   Takes 30 seconds           │
└──────────────────────────────┘
```

### Implementation

**New endpoint: `previewAds`** — `modules/ai.js`

```js
exports.previewAds = onRequest({
  invoker: 'public',
  secrets: ['ANTHROPIC_API_KEY', 'GEMINI_API_KEY'],
  timeoutSeconds: 60,
}, async (req, res) => { ... });
```

This is the one endpoint in the system that is intentionally unauthenticated, because requiring auth defeats its entire purpose. That makes abuse control mandatory, not optional:

- **IP rate limit**: 3 previews per IP per hour, stored in `previewRateLimit/{ipHash}` where `ipHash` is a SHA-256 of the IP (never store raw IPs). Reuse the `checkUidRateLimit` transaction pattern with the hash as the key.
- **Global daily cap**: a counter at `config/previewBudget` with a hard daily ceiling (start at 500). When exceeded, return a canned sample instead of calling the model. A capped bill beats an uncapped one.
- **Input limits**: `bizName` ≤ 80 chars, `city` ≤ 60 chars. Reject anything longer before the model call.
- **Cache**: key on `sha256(bizName|city)` in `previewCache/{hash}` with a 7-day TTL. Someone refreshing the page costs nothing.

**Flow inside the endpoint:**

1. Rate limit + budget check
2. Cache lookup — return on hit
3. `suggestCategory` logic on `bizName` to infer the category
4. `adaptListing`'s prompt builder with a minimal listing: `{ bizName, city, category }`, `platforms: ['google','facebook','instagram']`, `tone: 'friendly'`, empty `aiContext`
5. Write to cache, return

**Frontend:** new `BlastyBiz-Preview.html`, set as the landing target from the marketing site. On "Save these," write the three generated adaptations plus `bizName`, `city`, and the inferred category into `sessionStorage` under `bb_preview`, then route into signup. After account creation, `CreateBiz` reads `bb_preview` and pre-fills — so the owner's first authenticated screen already has their business in it and their ads waiting.

### Edge cases

- **Model failure**: never show an error on this page. Fall back to a generic-but-plausible template with the business name substituted in. A mediocre ad converts better than an error state.
- **Cache poisoning**: cache key is derived from user input, so cached content is per-input. Escape all output — this is a pre-auth page rendering model output, and `escHtml` is mandatory on every insertion point.
- **Nonsense input**: if `suggestCategory` returns low confidence, use a generic "local business" category rather than refusing.

### Acceptance criteria

- Time from landing to three visible ads: under 25 seconds on 4G
- Zero fields required beyond name and city
- Preview content survives signup and appears pre-filled in the first business
- An unauthenticated caller cannot exceed 3 previews/hour or contribute to more than the daily budget

## Spec 2 — Extract the Story instead of asking for it

**Effort: Low (1 endpoint, 1 screen change). Impact: Highest quality lever.**

### Problem

`aiContext` is the single biggest determinant of ad quality. `modules/ai.js:133–143` weaves all five fields directly into the prompt under "the owner's voice — weave this authenticity naturally into every platform's copy."

It is also five free-text boxes asking a busy contractor to describe his brand story, what makes him different, his awards, and his ideal customer. On a phone. It is the most-skipped step in the product, and when it is skipped every downstream ad is generic — which is the exact failure the product exists to prevent.

`replit.md` carries this as an open question: should Blasty nudge people who skipped Story? Nudging is the wrong answer. The right answer is not to ask.

### Solution

Ask for one thing the owner already has — a website URL, a Facebook page, or a Google Business Profile — and draft all five `aiContext` fields from it. The owner edits rather than authors.

```
┌──────────────────────────────┐
│  Tell us about your business │
│                              │
│  Paste a link and we'll do   │
│  the rest.                   │
│  ┌────────────────────────┐  │
│  │ perrysauto.com         │  │
│  └────────────────────────┘  │
│                              │
│     [ Fill this in for me ]  │
│                              │
│  or write it yourself →      │
└──────────────────────────────┘
```

Then the five fields, pre-filled, each editable, each with a subtle "we guessed this — fix anything wrong" affordance.

### Implementation

**New endpoint: `extractBizContext`** — `modules/ai.js`

```js
exports.extractBizContext = onRequest({
  invoker: 'public',
  secrets: ['ANTHROPIC_API_KEY', 'GEMINI_API_KEY'],
  timeoutSeconds: 90,
}, withAuth(async (req, res, decoded) => { ... }));
```

Input: `{ bizId, sourceUrl }` or `{ bizId, source: 'google' }`.

**Two source paths:**

1. **URL** — fetch the page, strip to text, feed to the model with a prompt asking it to fill the five `aiContext` fields and return strict JSON. Return `null` for any field it cannot ground in the source rather than inventing one.
2. **Google Business Profile** — no fetch needed. The connection already exists and already carries `business.manage` scope. Read the location's `profile.description`, `categories`, and attributes via `mybusiness.googleapis.com/v4/accounts/{acct}/locations/{loc}` and feed that instead. **This path is strictly preferable** — no SSRF surface, higher-quality structured input, and zero typing since the owner has already connected Google.

**Security — this is the critical part.** Fetching a user-supplied URL server-side is an SSRF primitive, and `fetchWithTimeout` (`lib/shared.js:224`) has no address validation. This exact class of bug was a release blocker on Litigant AI. Requirements:

- Scheme allowlist: `https` only
- Resolve the hostname **before** connecting and reject any address in a private or reserved range — `10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`, `::1`, `fc00::/7`
- Re-validate after every redirect; cap redirects at 3
- Response size cap of 2 MB, timeout of 10 seconds
- Never return the raw fetched body to the client — only the extracted fields

Write a dedicated `safeFetchUrl()` in `lib/shared.js` rather than hardening `fetchWithTimeout`, so the safe version is unmistakable at the call site.

**Cost:** one `reserveAiAction` per extraction. Cache the result on the business document as `aiContextSource: { url, extractedAt }` so re-running is a deliberate act.

### Edge cases

- **Thin or JS-only site**: if extracted text is under ~200 chars, don't call the model. Say "we couldn't read much from that page" and fall through to manual entry with no fields pre-filled.
- **Wrong business**: the owner is editing, so a wrong guess is recoverable. But mark extracted fields visually distinct from typed ones until the owner touches them, so nothing false ships silently into every ad.
- **Awards field**: the most likely to be hallucinated. Instruct the model explicitly to leave `awards` null unless the source states one.

### Acceptance criteria

- Google-connected owner reaches a fully populated `aiContext` with zero typing
- URL path populates at least `story` and `different` for a typical small-business homepage
- No request to a private IP range is ever issued, verified by test
- Manual entry remains available and unchanged

## Spec 3 — Approval queue, not a composer

**Effort: High (new email flow, new endpoints, product-shape change). Impact: Defines the product.**

### Problem

The current model requires the owner to open the app, navigate to a draft, and act. A busy contractor will not do this weekly. He will do it twice, then stop, then churn — while still believing the product "works," because it did when he used it.

Retention for this product is not a function of ad quality. It is a function of whether the ads keep going out when the owner stops paying attention.

### Solution

The owner never opens the app. Thursday morning, an email:

```
Subject: Your Friday post is ready — Perry's Auto Repair

  ┌────────────────────────────┐
  │ [photo]                    │
  │                            │
  │ "Toledo drivers: brake     │
  │  season is here. We're     │
  │  running free inspections  │
  │  through the 15th..."      │
  │                            │
  │ Posting Friday 9:00 AM to  │
  │ Google · Facebook · Insta  │
  └────────────────────────────┘

     [ Approve ]  [ Change ]  [ Skip ]

  Or do nothing — we'll post it Friday.
```

Note the last line. **Silence is approval.** A product requiring weekly action fails on the week the owner is busy — which is every week. Inverting the default is the entire point: the system runs, and the owner intervenes only to stop or steer it.

### Implementation

**Signed action links.** `modules/misc.js:117–122` already implements exactly the pattern needed — HMAC signature, `timingSafeEqual` comparison, dedicated signing key. Extend it:

```js
function makeActionSig(uid, draftId, action, key) {
  return crypto.createHmac('sha256', key)
    .update(`${uid}:${draftId}:${action}`)
    .digest('hex');
}
```

**New endpoint: `draftAction`** — `modules/publishing.js`, `invoker: 'public'`, no bearer required (the signature is the auth). Accepts `?uid=&draft=&action=approve|skip|change&sig=`.

- `approve` → set `schedule.approved = true`, return a confirmation page
- `skip` → advance `schedule.nextRunAt` by one interval, no post this cycle
- `change` → redirect into the app at that draft, auth-gated normally

Requirements: reuse `UNSUB_SIGNING_KEY`'s pattern with a separate `ACTION_SIGNING_KEY`; make links single-use by recording `draftActions/{uid}_{draftId}_{cycle}`; expire links after 14 days.

**New scheduled function: `scheduledDraftPreview`** — runs daily, finds drafts whose `schedule.nextRunAt` falls within the next 48 hours and that have not had a preview sent this cycle, generates the content if not already generated, and sends the email. Mark `schedule.previewSentAt` to prevent duplicates.

**Change to `scheduledPostingCheck`**: respect `schedule.skipCycle` if the owner clicked Skip. Do **not** require `approved === true` — that would break the silence-is-approval model.

### The critical safeguard

Auto-posting without explicit approval is right for retention and wrong if the content is ever bad. Three guards:

1. **First three posts require explicit approval.** New owners opt into trust; they don't start there. After three approvals, switch to silence-is-approval and tell them you're doing it.
2. **Any post the model flags as low-confidence requires approval**, regardless of history.
3. **One-click global pause** in every email footer, honoured immediately.

### Edge cases

- **Email in spam**: silence-is-approval means an unseen email still posts. Mitigate by requiring at least one email open or click in the prior 30 days before auto-posting; fall back to approval-required if the owner has gone dark entirely.
- **Stale content**: a draft written six weeks ago about a seasonal promotion should not auto-post. Expire generated content after 14 days and regenerate.
- **Multi-business owners**: one email per business, not a digest. A digest turns three decisions into one deferred decision.

### Acceptance criteria

- An owner who never opens the app after setup still has posts going out at 90 days
- Approve and Skip both work from an email client with images disabled
- Pause is honoured within one cron cycle
- No post goes out under silence-is-approval before three explicit approvals

## Spec 4 — Import photos from Google Business Profile

**Effort: Low–Medium (1 endpoint, 1 UI addition). Impact: Removes the most common stall point.**

### Problem

Ads with photos outperform ads without them, and most small businesses have neither good photos nor the patience to upload them from a phone. The upload path (`BlastyBiz.html:5560`) is a real step with a real failure rate, and it sits between the owner and their first post.

Meanwhile, every owner who connects Google has already uploaded photos to their Google Business Profile — usually their best ones, often professionally taken.

### Solution

On Google connect, import their existing GBP photos into the media library automatically. The owner's library is populated before they know they have one.

### Implementation

**New endpoint: `importGooglePhotos`** — `modules/oauth.js` or `modules/publishing.js`.

Called automatically at the end of the Google OAuth callback (fire-and-forget into a job document, not inline — the callback should stay fast), and available as a manual "Re-import from Google" button.

1. `_getConnTokens` for the Google connection
2. `GET https://mybusiness.googleapis.com/v4/accounts/{acct}/locations/{loc}/media` — the `business.manage` scope already covers this, so **no re-consent is required**
3. For each media item up to a cap of 20: download, validate with the existing magic-byte checks, upload to `photos/{uid}/global/`, and write a library entry with `source: 'google_import'`
4. Skip duplicates by content hash

**Constraints:**

- Cap at 20 photos and 5 MB each
- Run as a background job with progress written to Firestore so the UI can show "importing 7 of 12…"
- Never block the OAuth callback on this

### Edge cases

- **No photos on GBP**: silent no-op. Never surface "we found nothing."
- **Rate limits**: GBP APIs are quota-limited. Back off and resume rather than failing the import.
- **Ownership**: these are the owner's own photos from their own listing, so rights are clean — but mark them `source: 'google_import'` so they are distinguishable if a dispute ever arises, and delete them with the account like any other photo.

### Acceptance criteria

- An owner connecting Google has a populated photo library without a single upload
- Import never delays or fails the OAuth callback
- Imported photos are deleted by `deleteAccount` along with everything else under `photos/{uid}/`

## Spec 5 — Let the manual platform list shrink

**Effort: Low (data model + UI). Impact: Changes the emotional register of the product.**

### Problem

Three platforms post automatically. Twelve are copy-and-paste. The one-tap copy-and-open-tab at `BlastyBiz.html:1599` is already good — that part is not the problem.

The problem is that twelve platforms are shown, forever, with no memory of what the owner did. A permanently incomplete checklist reads as twelve chores you are failing at. Most owners care about three or four platforms. The other eight are noise that makes the product feel like homework.

### Solution

Two additions: confirm what got posted, and let the list shrink to what the owner actually uses.

```
┌──────────────────────────────┐
│ Copy & post                  │
│                              │
│ ✓ Yelp        posted Mar 3   │
│ ✓ Nextdoor    posted Mar 3   │
│ ○ Alignable   [ Copy & go ]  │
│                              │
│  ─ Not using (8) ────────  ▾ │
└──────────────────────────────┘
```

After the copy-and-open action fires, on return to the tab, ask once: **"Did it post?"** → `[Yes] [Not yet]`. Yes marks it done for that draft and logs it. Anything the owner marks "not for me" collapses into a folded section they can reopen.

### Implementation

**Data**: `platformPrefs` map on the business document —

```js
platformPrefs: {
  yelp:      { status: 'active',   lastPostedAt: <ts> },
  alignable: { status: 'dismissed' },
}
```

**Draft-level**: `manualPosted: { yelp: <ts>, nextdoor: <ts> }` on the listing draft.

**Rules**: both are owner-writable and must be added to the `hasOnly` allowlist in `firestore.rules` — the rules are now an allowlist, so new fields fail closed until explicitly permitted. This is the mechanical enforcement working as designed; do not skip it.

**Detection**: use the `visibilitychange` event to detect return-to-tab after the copy action, then show the confirm. Do not use a timer.

### Edge cases

- **Never confirms**: after three unconfirmed copy actions on the same platform, stop asking. Assume it worked.
- **Dismissed everything**: if all twelve are dismissed, show a single quiet line offering to bring them back. Never re-expand automatically.
- **New platform added later**: default new platforms to `active` but surface them in a "new" state rather than mixed into the main list.

### Acceptance criteria

- The manual list reflects only platforms the owner has not dismissed
- Confirmation is one tap and never blocks anything
- Dismissals persist across sessions and devices

## Spec 6 — Don't meter the retry

**Effort: Trivial (a few lines). Impact: Disproportionate to effort.**

### Problem

Starter plans get 10 AI actions per month (`getPlanConfig`, `lib/shared.js`). If regenerating a draft the owner doesn't like costs one of those, the owner rations. Rationing means accepting a first draft that is merely acceptable — which means the ads that go out are worse than the ads the system can produce, which means the product underperforms its own capability at exactly the moment the owner is deciding whether to keep paying.

The emotional register matters here. "Careful, you're using them up" is a bad feeling to attach to the core action of the product.

### Solution

The first regeneration of any given draft is free.

### Implementation

In `reserveAiAction`, accept an optional context:

```js
async function reserveAiAction(uid, opts = {}) {
  const { draftId, isRegeneration } = opts;
  if (isRegeneration && draftId) {
    const freeKey = `freeRegen_${draftId}`;
    // inside the existing transaction: if this draft has not used its
    // free regeneration, consume that instead of a plan action
  }
  ...
}
```

Track consumed free regenerations as a `freeRegenUsed: true` flag on the draft document rather than a separate collection — it is per-draft state and belongs with the draft.

**UI**: label the button "Try again (free)" the first time and "Try again (1 credit)" thereafter. Being explicit about which one is free is most of the benefit.

### Edge cases

- **Abuse**: bounded by construction — one free regeneration per draft, and draft creation is itself gated by plan limits.
- **Interaction with dedup**: `adaptListing` dedups on `requestId` (`modules/ai.js:102–107`). A regeneration must send a **new** `requestId`, or it will return the cached prior result and consume nothing while appearing to do nothing.

### Acceptance criteria

- First regeneration per draft does not decrement the plan counter
- The UI states which regenerations are free before the tap
- A regeneration always produces new content, never a dedup cache hit

## Sequencing

**Phase 1 — cheapest, highest impact.** Specs 2 and 6. Both are small, both are self-contained, both immediately improve output quality. Spec 2 in particular fixes the thin-`aiContext` problem that currently degrades every ad from every owner who skipped Story.

**Phase 2 — acquisition.** Spec 1. Requires the abuse controls to be right before it ships, but changes what the top of the funnel feels like more than anything else on this list.

**Phase 3 — reduce stalls.** Specs 4 and 5. Both remove friction from owners who are already in the product.

**Phase 4 — retention.** Spec 3. The largest change and the one that most affects whether owners are still customers at 90 days. It deserves its own design pass and probably its own document.

---

## One caution

Spec 3 changes what BlastyBiz *is* — from a tool the owner uses into a service that runs on the owner's behalf. That is almost certainly the right direction, and it is the version that survives the owner getting busy.

But it also means the system posts to a real business's public listings without a human reading it first. The three safeguards in that spec are not optional decoration. A single bad auto-post to a customer's Google Business Profile is a worse outcome than a hundred posts that never went out, because the first one is visible to that customer's customers and the second is only visible to you.

Build the safeguards in the same pass as the feature, not after.
