## 1. Release blockers

### B1 — Free-regeneration bypass gives unlimited AI `VERIFIED` — highest priority

Two separate defects that compose into a full bypass of the AI credit cap.

**Defect 1 — the free path returns before the cap is checked.**
`functions/lib/shared.js:249-256`:

```
if (isRegeneration && draftRef && draftSnap && draftSnap.exists && !draftSnap.data()?.freeRegenUsed) {
  tx.set(draftRef, { freeRegenUsed: true }, { merge: true });
  return { plan, used, cap, freeRegen: true };     // ← line 251, returns here
}
if (used >= cap) {                                  // ← line 254, never reached
  throw Object.assign(new Error('LIMIT_REACHED'), { used, cap, plan });
}
```

A user sitting at 100/100 still gets a generation on any draft that hasn't spent
its free regen.

**Defect 2 — `freeRegenUsed` is client-writable.**
`firestore.rules:167-169`, the `listingDrafts` update rule, blocks exactly one
field:

```
allow update: if request.auth != null &&
  request.auth.uid == userId &&
  !('uid' in request.resource.data.diff(resource.data).affectedKeys());
```

`freeRegenUsed` is not protected. The owner can set it back to `false` from the
browser and repeat.

**Two independent exploit paths:**
1. Reset `freeRegenUsed: false` on one draft, call `adaptListing` with
   `isRegeneration: true`, repeat. Unlimited.
2. Don't even bother — draft *create* is unrestricted (`firestore.rules:165-166`).
   Create N drafts, fire one "regeneration" at each. N free generations, counter
   never moves.

`adaptListing` takes `isRegeneration`, `draftId` and `businessId` straight from the
request body (`functions/modules/ai.js:511-512, 527`), so both are one fetch call.

**Fix — needs all three:**
1. Move the cap check **above** the free-regen branch in `shared.js`. Free regen
   should skip the *decrement*, not the *gate*.
2. Add `freeRegenUsed` to a server-only denylist in the `listingDrafts` update
   rule: `!request.resource.data.diff(resource.data).affectedKeys().hasAny(['uid','freeRegenUsed'])`.
3. Cap free regens per *user per period*, not per draft — per-draft is unbounded
   because drafts are unbounded.

### B2 — `suggestCategory` is unauthenticated with a spoofable limiter `VERIFIED`

`functions/modules/ai.js:83` — `onRequest({ invoker: 'public' }, async (req, res) => {`.
No `withAuth`. No bearer check anywhere in the handler. Anyone on the internet can
call it, and each call makes **two** Gemini requests (`ai.js:147` and `ai.js:163`).

Three things make this worse than it looks:

1. **The IP is attacker-supplied.** `ai.js:87`:
   `((req.headers['x-forwarded-for'] || '').split(',')[0].trim())` — taking index
   `[0]` takes the *client-sent* value, not the load balancer's appended one.
   Rotate the header, get a fresh 10/hour bucket every request.
2. **The limiter fails open.** `shared.js:441` — `catch(e) { return true; }`.
   Any Firestore error means "allowed", silently, with no log.
3. **No global budget.** `previewAds` has a 500/day ceiling (`ai.js:230-243`).
   `suggestCategory` has nothing equivalent.

**Also:** it bypasses `getAiSettings()` entirely and hardcodes
`gemini-flash-lite-latest` at `ai.js:131`, so your admin provider switch has no
effect here. And it never calls `trackAiUsage`, so these calls are **invisible in
`aiUsageLogs`** — the spend won't show up in your own dashboard.

**Fix:** wrap in `withAuth`, or if it must stay pre-auth, add the same
`config/previewBudget`-style global daily ceiling that `previewAds` has, key the
limiter off `req.ip` rather than the header, and route through `callAI` +
`trackAiUsage`.

| `platform-categories.js` | no version |
| `activity-ping.js`, `header-loader.js`, `firebase-init-v2.js` | no version |

`firebase.json:62-68` serves `**/*.js` with `max-age=3600, stale-while-revalidate=86400`.
So a fix to `auth-guard.js` or `admin-guard.js` can be served stale for up to **25
hours** with no way to force it. Those are your two authorisation files.

**Blind spot in the gate:** `check-release.cjs:121-141` builds its regex as
`asset + '\\?v=([^\\s"\']+)'`, so an *unversioned* reference is invisible. `mascot.js`
has one versioned reference and one bare one — `versions.size === 1`, so Check 3
reports ✅ while the bare reference is uncacheable-busted.
**Fix:** extend `bump-css-version.cjs` to all six `VERSIONED_ASSETS`, and extend
Check 3 to fail on any bare reference to a versioned asset.

### M13 — Customer preview emails drift on every deploy `VERIFIED`
`scheduled.js:263` — `scheduledDraftPreview` uses `schedule: 'every 24 hours'`.
Interval schedules anchor to deploy time, not wall-clock. Combined with
`replit.md`'s "Deploy after every change — no exceptions", the daily customer
preview email moves to a new hour every deploy. Owners will see it arrive at 3am.
Same applies to `cleanupAbandonedSignups` (`scheduled.js:700`), which matters less.
**Fix:** `'every day 09:00'` with `timeZone: 'America/New_York'`, matching the
other four.

### M14 — The rate limiter fails open, silently `VERIFIED`
`shared.js:441` — `catch(e) { return true; }`. No log line, no metric. Every
consumer inherits it: `checkoutRateLimit` (`payments.js:101`),
`extractBizContextRate` (`ai.js:325`), `previewRateLimit` (`ai.js:221`),
`suggestCategoryRateLimit` (`ai.js:91`).

`ai.js:221` also does `.catch(() => false)` on the result — dead code, since the

**Fix:** at minimum `bbLog('WARNING', ...)` before returning. Consider fail-closed

### M15 — GBP import progress is written but never read `VERIFIED`
`_runGooglePhotoImport` maintains a detailed progress doc — `status`, `total`,

`importJobs` appears in **no file under `public/`** (grepped), and it has no entry

## 6. The pattern underneath most of this

Nine of these findings are the same shape: **a fact stored in more than one place,
with a comment asking a human to keep them aligned.** The capability map (H1), the
publishers (H2), the category lists (M6), the platform lists in the prompts (H4),
the Graph version (B4), the opt-out check (M8), the project URL (L7), the asset
versions (M11).

Every one of them is currently *correct or nearly correct* — and every one is one
edit away from silently diverging, with nothing in the build to notice.

`escape-utils.js` (R4) is the counter-example and it's the model: one implementation,
a mechanical check in `check-release.cjs`, verified clean. The gap isn't that you
don't know the pattern — it's that `check-release.cjs` isn't running. Wiring it in
(B5) turns the enforcement you already wrote from documentation into a gate, which
is exactly the property you need before agents are editing this tree.
