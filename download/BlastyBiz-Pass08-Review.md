# BlastyBiz Pass 08 — ten assessed repairs

Source: the production repair assessment's remaining groups, checked against the code. This pass adds ten new repair groups; Pass 06/07 reviewer corrections are not counted again.

Baseline: corrected Pass 07, pushed to `FlubaDesigns/Blastybiz-repo` main as `91dc188d09bf8532ea483fa72c7e9807af17f5d1`. Local pre-pass commit `1403a17` has the same tree. Pass 08 is a local review candidate, not pushed or deployed.

| Group | Implemented behavior |
| --- | --- |
| R02 | Profile and new CreateBiz submissions call the existing createBusiness endpoint with a stable business ID. It checks every existing business, including incomplete setup, and commits the business, account pointer and optional initial campaign atomically. Concurrent creations serialize through the account record. Browser business creation is denied; ordinary business editing remains available. Capacity failures are visible without losing answers. |
| R09 | The existing hourly worker transactionally reads the current draft, account, business and campaign; it creates deterministic per-cycle jobs and a server-only receipt before advancing the schedule. Overlapping invocations cannot create duplicate jobs for that occurrence. No provider calls occur in the schedule transaction. |
| R10 | Removed the scheduler's three duplicate publisher adapters. Recurring delivery now uses existing publishJobs and dispatchPublishJob, including existing status, retry and uncertainty handling. Facebook's canonical adapter now sends selected photos, staging multi-photo attachments before one final publication. Successful explicitly approved occurrences increment business approvalCount once through the existing completion trigger. |
| R11 | Recurring jobs and previews use the saved draft selection, excluding destinations explicitly excluded during review. New and regenerated drafts save enabledPlatforms; selection changes persist to the current draft; final review saves the approved subset. Legacy drafts without explicit destinations pause for owner selection rather than treating old copy as permission to publish. |
| R12 | A cycle advances only in the same transaction that saves all selected destination jobs and their copy/images. Every destination retains its own result, retry state or manual action. Failed jobs remain actionable; retrying one job does not recreate successful destinations. Missing selected copy pauses the draft instead of silently dropping part of the cycle. |
| R13 | Both workers query due work and use pages of 200 ordered by nextRunAt and document identity. A persisted cursor continues after the bounded 25-page invocation budget, so blocked early records cannot permanently hide later ones. Added the corresponding collection-group index. |
| R21 | Square event completion and account/business/subscription effects commit in one transaction. Unfinished database work returns HTTP 503 for redelivery. Checkout linkage is retained with fulfillment evidence; reopening an idempotent checkout cannot overwrite that evidence. Previously received-only event markers can retry when their linkage still exists. |
| R22 | Subscription snapshots and customer linkage are retained in the existing webhookEvents ledger. A shared customer record serializes payment/subscription races. Payment-first and subscription-first order both link; legacy plan IDs and current variation IDs are supported. Version ordering rejects stale subscription updates. |
| R23 | Cancellation applies to the matching active subscription. Older subscription cancellations cannot revoke a replacement, including the interval before its new subscription ID arrives. Subscription creation time is checked against the checkout, and already-canceled subscriptions cannot be reactivated by a delayed payment event. |
| R30 | Campaign removal archives the existing campaign and preserves its subcollections/history. Draft schedules are disabled in pages; workers also check campaign status so a failed cleanup cannot resume future work. The dispatcher and admin retry reject removed campaigns, and direct draft approval rejects archived campaigns. Active lists omit archived campaigns. The UI waits for server success and retains the campaign on failure. |
